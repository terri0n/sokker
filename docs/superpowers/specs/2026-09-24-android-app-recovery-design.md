# Sokker Asistente Android recovery and Google Play publication design

Date: 2026-09-24
Status: design for review

## Goal

Recover the existing Sokker Asistente Android application into the `terri0n/sokker` repository, preserve the observable behavior of the last deployed APK, adapt its Sokker request proxy to the current `X-Sokker-Client` identification flow, and leave the project ready to build an Android App Bundle for a first Google Play release.

This is not a rewrite of the Android application. The recovered APK and Android Studio project are the behavioral reference.

## Known deployed baseline

The recovered production APK has already been inspected and matched byte-for-byte with the release APK contained in the recovered Android project archive.

Known application identity and behavior:

- application/package id: `com.formulamanager.sokker.asistente`
- previous version: `versionCode 10`, `versionName 1.10`
- previous `minSdk`: 21
- previous `compileSdk` / `targetSdk`: 35
- launcher: `MainActivity`
- one full-screen `WebView`
- initial URL: `https://raqueto.com/sokker/asistente`
- JavaScript enabled
- zoom enabled, built-in zoom controls hidden
- custom JavaScript `alert` / `confirm` handling
- browser back navigates WebView history before exiting the Activity
- requests whose URL starts with `https://sokker.org` are intercepted natively

The previous proxy reconstructs a POST body from `ilogin` and `ipassword` query parameters because `WebResourceRequest` does not expose a WebView POST request body. It does not forward `WebResourceRequest.getRequestHeaders()`, which means the current `X-Sokker-Client` header generated by the web application is lost inside the Android app.

## Distribution and signing

This application has never been published on Google Play. We therefore do not need to preserve the private key used to sign the old sideloaded APK.

The first Google Play release will establish a new signing identity through Play App Signing. A new upload key may be generated for the project/release process. No private key, keystore, password, `key.properties`, or equivalent signing secret will be committed to Git.

Keeping the existing package id is desirable because it preserves the application's identity and existing links/configuration. However, an APK signed with the new key cannot be installed as an in-place update over the old sideloaded APK with the same package id. Existing sideload users would have to uninstall the old build before installing the new Play-signed build. This is acceptable for this migration.

New Google Play apps currently must target Android 16 / API level 36 or higher for submissions after 2026-08-31. The recovered project will therefore be migrated to `compileSdk 36` and `targetSdk 36` while retaining `minSdk 21` unless build compatibility forces a separately reviewed change.

Google Play requires new applications to be published as Android App Bundles and Play App Signing is required for new apps using AAB. The release artifact for Play will therefore be `.aab`, not a committed APK.

References:

- https://support.google.com/googleplay/android-developer/answer/11926878
- https://developer.android.com/guide/app-bundle
- https://support.google.com/googleplay/android-developer/answer/9842756

## Repository layout

Add the recovered project under:

`android/SokkerAsistente/`

The repository should contain only reproducible project inputs:

- Gradle settings and build scripts
- Gradle wrapper files
- application source
- manifest
- layouts and Android resources
- ProGuard/R8 rules if present
- project documentation needed to build/release

The repository must not contain:

- `.gradle/`
- `build/` or `app/build/`
- generated APK/AAB files
- Android Studio machine-local files that are not required by the build
- `local.properties`
- keystores (`*.jks`, `*.keystore`)
- signing passwords or signing property files

The Android subtree will have its own `.gitignore` if the repository root rules are not sufficient.

## Versioning

Initial recovered Play-ready build:

- `versionCode 11`
- `versionName 1.11`

Using 11 keeps monotonic versioning relative to the last distributed APK even though Google Play has not seen the previous releases.

## WebView architecture

The application remains a thin native shell around the server-hosted Sokker Asistente web application.

No native duplicate of server screens, authentication state, player data, or `.properties` persistence will be introduced.

`MainActivity` remains responsible for:

1. configuring the WebView;
2. loading `https://raqueto.com/sokker/asistente`;
3. handling back navigation;
4. handling the existing JavaScript dialogs/custom-view behavior;
5. intercepting only requests that need the Sokker native proxy.

This preserves the deployed architecture and avoids creating a second application state model.

## Sokker proxy design

### Scope

The proxy is intended only to bypass browser CORS restrictions for direct requests from the hosted web application to `https://sokker.org`.

It must not become a general-purpose HTTP client or a second Sokker API implementation.

### Request identification header

For intercepted Sokker requests:

- copy the request headers available from `WebResourceRequest.getRequestHeaders()` when they are safe to forward;
- preserve `X-Sokker-Client` if it is already present;
- if `X-Sokker-Client` is missing, add the same public client identifier used by the server/web utility layer;
- do not treat this identifier as a secret.

The Android constant and the web/server constant must be kept logically identical. A regression test should make divergence visible.

### Legacy XML-session login

Current browser-side direct Sokker POSTs are the legacy login/session calls to:

`https://sokker.org/start.php?session=xml&ilogin=...&ipassword=...`

The web application already places the encoded `ilogin` and `ipassword` values both in the query string and in the form POST data.

Because WebView interception does not expose the original POST body, Android may reconstruct the form body from the URL query parameters, but only when all of these are true:

- host is `sokker.org`;
- path is `/start.php`;
- query contains `session=xml`;
- the request method requires the legacy form POST behavior;
- `ilogin` and `ipassword` are present.

The reconstructed body is:

`ilogin=<encoded value>&ipassword=<encoded value>`

with an appropriate form content type.

This deliberately narrows the old behavior. The deployed APK effectively synthesized credentials for every intercepted Sokker request. The recovered implementation must not attach login credentials to unrelated Sokker endpoints.

### Other Sokker requests

For other intercepted requests:

- preserve the original HTTP method where supported by the current proxy path;
- do not invent a request body;
- do not append credentials;
- preserve relevant request headers including `X-Sokker-Client`;
- return the real status, content type, encoding, response headers and response stream as faithfully as Android's `WebResourceResponse` allows.

If a future web feature needs an arbitrary POST body to Sokker, that requirement must trigger a separate design. We will not add a JavaScript bridge pre-emptively.

### CORS response behavior

The native response must continue to provide the response-side CORS headers needed by the hosted page to consume the proxied result.

Request-side `Access-Control-Allow-Origin` / `Access-Control-Allow-Methods` headers from the old APK are not authoritative CORS controls and need not be propagated unless testing proves an endpoint depends on them.

### Error handling

The proxy should distinguish normal HTTP error responses from transport failures:

- HTTP 4xx/5xx should still return a `WebResourceResponse` using the connection's error stream when available;
- transport/proxy exceptions should be logged and should fail without leaking credentials;
- no password or reconstructed body should be written to logs.

The implementation should avoid relying exclusively on `HttpURLConnection.getInputStream()`, because it throws for HTTP error responses.

## Compatibility behavior to preserve

The recovered app must preserve:

- initial Asistente URL;
- JavaScript support;
- WebView zoom behavior;
- JavaScript alert and confirm dialogs;
- back-button history behavior;
- current orientation/configuration handling;
- non-Sokker web navigation behavior;
- legacy Sokker login from the WebView;
- response consumption by the current `sokkerPost` JavaScript utility.

No unrelated native UI redesign is part of this work.

## Android 16 / API 36 migration

The project will be built against API 36 and the build tooling/dependencies will be updated only as far as necessary for a supported API-36 build.

The migration must preserve `minSdk 21` if possible. Any API-36 behavioral change affecting WebView networking, cleartext policy, exported components, back navigation, edge-to-edge rendering, or manifest requirements must be handled explicitly rather than hidden behind a broad dependency upgrade.

The source should remain Java unless a concrete requirement forces Kotlin. The recovered project currently includes the Kotlin plugin/stdlib despite the application code being Java; unnecessary Kotlin build dependencies may be removed only if verification shows they are not required.

## Tests and verification

### Native unit tests

Extract small proxy decisions into package-visible/static helpers where useful so they can be tested without a real WebView. Tests should cover at least:

1. Sokker URL recognition;
2. non-Sokker URL exclusion;
3. legacy `/start.php?session=xml` recognition;
4. reconstruction of the legacy login body;
5. no credentials for unrelated endpoints;
6. forwarding/preservation of `X-Sokker-Client`;
7. insertion of `X-Sokker-Client` when absent;
8. no logging of credentials.

### Integration/manual checks

At minimum:

1. debug build installs and launches;
2. `https://raqueto.com/sokker/asistente` loads;
3. normal navigation works;
4. back navigation uses WebView history;
5. JavaScript alert/confirm still work;
6. Sokker legacy login succeeds through the native proxy;
7. Sokker sees the `X-Sokker-Client` identifier;
8. a failed Sokker login returns the real failure to JavaScript instead of a proxy exception;
9. non-Sokker requests are not intercepted;
10. release bundle task produces a non-empty `.aab`.

### Google Play readiness

Before calling the project Play-ready:

- release build targets API 36;
- `versionCode` and `versionName` are correct;
- package id remains intentional;
- AAB builds successfully;
- no secret/signing file is tracked by Git;
- Play upload key setup is documented but not stored in the repository;
- the release can be exercised through Play internal testing when Play Console setup is available.

## CI

Add a separate Android CI workflow rather than coupling Android failures to the existing Java 8 server workflow.

The Android workflow should, at minimum:

- set up a supported JDK for the chosen Android Gradle Plugin;
- run the native tests;
- build the debug APK as a compile/package verification artifact;
- build the unsigned or CI-safe release bundle when feasible without repository secrets.

Signing of production Play uploads must remain outside normal public CI unless protected repository secrets are deliberately configured later.

## Security and data handling

Credentials remain transient login data. The Android app must not persist Sokker passwords, add credential logging, or introduce native storage for them.

The proxy must scope credential reconstruction strictly to the known legacy XML-session login request.

`X-Sokker-Client` is an application identifier, not a password or private API secret.

## Non-goals

This work does not include:

- rewriting the server application as native Android screens;
- replacing the server's `.properties` persistence;
- migrating every remaining server-side XML fallback to JSON;
- adding arbitrary native Sokker API clients;
- redesigning the WebView login protocol;
- publishing store listing copy/screenshots/privacy forms;
- preserving update compatibility with the old sideload signing key;
- changing the server-side `sokkerPost` fallback behavior.

## Implementation sequence

After this design is approved, the implementation plan should sequence the work so each stage is independently verifiable:

1. recover only the clean Android project inputs into the repository;
2. establish a reproducible baseline build;
3. migrate build configuration to API 36;
4. add proxy contract tests and demonstrate the current header-loss behavior;
5. implement the narrowly scoped proxy fixes;
6. run full Android verification;
7. add AAB/Play-ready build configuration and release documentation;
8. perform final repository-secret/artifact audit.

No server branch should be merged merely to make the Android project compile. Server recovery fixes remain separate changes and should be integrated according to their own verification state.
